## 2. D1 · 声音来源

**问题**：训练与发布的音色，声音从哪来？决定授权链条、数据采集章程与法务清单。

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| 🟢 **A 自录授权** | 本人或签署劳动合同/授权书的员工录制；逐人签《声音授权书》，明确用途、期限、可否再许可 | 需 5–30 小时有效语音（依基座而定，**目标值待 Phase 1 校准**）；音质取决于录音条件 |
| ⬜ **B 商业采购** | 向语音库/配音工作室购买授权 | 合同须覆盖「微调 + 发布权重 + 下游非商用再分发」，多数标准条款不覆盖，谈判成本高 |
| ⬜ **C 客户自带** | 客户提供声音并授权，项目方只做技术 | 每客户一套授权与鉴权（`E-LICENSE-002` 音色注册）；发布权重时无法包含他人音色 |
| ⛔ **D 合成生成** | 用现有 TTS 生成训练数据 | 多数基座许可禁止「用输出训练其他模型」（Fish Audio 明文禁止；R-18）；且质量上限受生成器限制，学术上属蒸馏 |

**建议理由**：合规路径最清晰（自己可控制授权范围），且与「禁商用 + 双授权」的发布策略天然一致；`manifest` 强制 `license_id` + 授权书引用已就位（[DATASET-MANIFEST-SPEC](../implement/data/DATASET-MANIFEST-SPEC.md)）。

**不拍板的后果**：**不能开始采集**（数据流水线第 ① 步即卡死），Phase 1 无法启动。

**拍板后改动**：`docs/implement/data/DATA-PIPELINE-SPEC.md` 的授权章节 + 新增授权书模板；D11 清单 L-1/L-2 具体化。

## 3. D2 · 首要场景

**问题**：产品首要形态是「实时对话」还是「离线内容生产」？决定流式优先级与 Q7 延迟是否硬指标。

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| 🟢 **A 实时对话优先** | 首字延迟与流式打断为一等公民；Q7 升为**硬指标** | 流式实现复杂度高（分块 vocoder + 状态缓存）；长文本吞吐需求后置 |
| ⬜ **B 离线内容生产优先** | 整段合成、追求吞吐与长文本稳定性；Q7 降为软指标 | 若后续要做对话，需重构流式链路 |
| ⬜ **C 两者并重** | 两条链路同时达标 | 档 B 排期吃不消，建议至少砍到 A 或 B 一个主场景 |

**建议理由**：AI 智能体的主战场是对话；契约（VoiceSpec）与 API 已按同一套设计，改主场景只需调整优先级不推翻契约。

**不拍板的后果**：`configs/eval/thresholds.yaml` 里 Q7 无法定「硬/软」，评估门禁口径悬空。

**拍板后改动**：thresholds.yaml 的 Q7 硬/软标记（**数值仍待校准，不在此表定**）；[DEPLOYMENT-SPEC](../implement/serve/DEPLOYMENT-SPEC.md) 压测口径。

## 4. D3 · 音色数量

**问题**：首版交付 1 个主音色，还是要多音色矩阵？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| 🟢 **A 1 个主音色** | 单音色做深（情感/语速/语调全参数打通） | 产品上不够「多角色」 |
| ⬜ **B 3–5 音色矩阵** | 多音色 + `voice_blend` 插值 | 档 C 排期；每音色都要独立数据与门禁；**`voice_blend` 且 `speaker_lock=false` 目前缺专用错误码**（见 §12） |
| ⬜ **C 客户定制多音色** | 按客户量产出音色 | 需音色注册 + 鉴权体系（`E-LICENSE-002`）+ 每客户授权 |

**建议理由**：先把「一个音色的参数化细调」做到可证明，再复制；架构上保留 `voice_blend` 字段，扩展不需改契约。

**不拍板的后果**：数据量目标与档位（档 B/C）无法定，排期承诺无依据。

## 5. D4 · 精确时长控制

**问题**：F4（按 `duration_ms` 精确出指定时长音频）是不是必须能力？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| ⬜ **A 必须支持** | 只选 `exact_duration=true` 的基座，评分卡里设为一票否决 | 候选收敛面变窄（IndexTTS2 有该能力但**权重无 license tag**，见 R-18）；可能被迫换基座 |
| 🟢 **B 保留能力不锁基座** | 契约保留 `duration_mode=exact`；基座不支持时返回 `E-CAPABILITY-001`，**不静默降级** | 用户体验上会看到「不支持」报错；需在 Phase 2 能力探测里如实标注 |
| ⬜ **C 不需要** | F4 降为 P2，`duration_mode` 只保留 `natural` | 若后续要做配音对轨（字幕/广告）需重开 |

**建议理由**：契约已能表达（v0.3 已落地），没有必要为了「必须」而现在砍掉候选；真实能力等 Phase 2 三候选同台实测（D19）再定，避免用猜测锁死基座。

**不拍板的后果**：基座评分卡权重无法定稿，Phase 2 定型无判据。

**拍板后改动**：[ADR-0002](ADR-0002.md) 评分卡「可控性」权重；`configs/base/base.template.yaml` 的 `capability_flags.exact_duration` 标注口径。

## 6. D5 · 云端商业 TTS 的角色

**问题**：是否允许调用云端商业 TTS（如商用 API）？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| 🟢 **A 仅作质量上限对照 / 兜底** | 离线评测时用云端 TTS 当作「人类可接受质量」参照；**不进交付物、不进训练数据** | 需在评测报告里注明来源与日期；不能拿它当回归基线 |
| ⬜ **B 完全不用** | 纯本地闭环 | 缺少外部质量参照，主观评测锚点弱 |
| ⛔ **C 生产兜底** | 线上不达标时回落到云端 TTS | 把云端许可与成本传导进交付物；与「本地权重 + 私有 API」的 D21 冲突；数据出境/隐私风险 |

**建议理由**：只做「参照物」不引入许可传导；这是既有 D21（本地权重 + 私有 API）能成立的前提。

**不拍板的后果**：评测体系里「质量上限参照」缺失，Q1–Q10 目标值缺少外部锚。

## 7. D6 · 算力档位（含 G0-4）

**问题**：训练与推理用什么硬件？决定档 B 能否承诺。

| 选项 | 规格 | 能做 / 不能做 |
| --- | --- | --- |
| ⬜ **A H-1 起步** | 1× 24GB（3090 / 4090 / A10 级），存储 1TB+ | 能做：LoRA、推理、评测、Phase 0–3 全链路跑通<br>不能做：全量 SFT、大 batch、偏好对齐（需顺延或租用） |
| 🟢 **B H-2 推荐** | 1× 80GB（A100/H100）**或** 4–8× 24GB，存储 1–5TB | 档 B 全流程，含偏好对齐（DPO）；成本与排期的平衡点 |
| ⬜ **C H-3 规模化** | 8× 80GB + 高速互联 + 对象存储 | 档 C、全量 SFT、多音色矩阵；无明确规模需求时不应上 |

**子问题（请一并回）**：自有硬件 / 租用云算力 / 两者混合？

**建议理由**：v0.1 起就建议的「省钱顺序」——先用 H-1 + 小数据跑通 P0–P3，拿到真实基线再决定是否升档；v0.4 按 H-2 估成本但**不采购、不承诺**。

**不拍板的后果**：**G0-4 未到位 → Phase 2 无法开始**；档 B 的 16–20 周排期不能对外承诺。

## 8. D8 · 语言范围

**问题**：首版支持哪些语言？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| ⬜ **A 仅中文（zh）** | 词典与评测只做中文 | 中英混读（技术名词、品牌名）会念错，属 R-11 零容忍范畴 |
| 🟢 **B 中文 + 中英混（zh / zh-en-mix）** | 双语言枚举 + `code_switch_policy` + 专名词典 | 需要中英混 golden_set 覆盖；词典维护成本中等 |
| ⬜ **C 加英语/日语等（zh / en / ja）** | 全量多语 | 词典、G2P、评测集、主观听审全部翻倍，档 C 起 |

**建议理由**：智能体对话里中英混是常态（AI/GPU/型号名），不做会直接掉到「念错」零容忍红线；加第三语言对首版收益低。

**不拍板的后果**：发音词典规模、golden_set 覆盖矩阵、Q3（字错率/CER）口径都无法定。

**拍板后改动**：`LinguisticSpec.lang` enum 是否需扩展（**当前已含 zh/en/zh-en-mix，改语言即改契约 → 需 v0.5 走 Spec 变更**）。

## 9. D9 · 情感粒度

**问题**：情感控制做到多细？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| ⬜ **A 仅 10 类离散** | 只用 `style.emotion` 枚举 | 同一类里「轻微难过」与「痛哭」无法区分 |
| 🟢 **B 10 类离散 + 连续强度** | `emotion` ∈ 10 类 **且** `emotion_strength` 0–1 连续 | 需 `emotion_strength` 过 5 点单调性扫描（阈值见 [thresholds.yaml](../../configs/eval/thresholds.yaml)）才开放 |
| ⬜ **C 加自然语言风格指令** | 允许 `style_prompt` 描述风格 | 描述不可严格复现；**`style_prompt` 不得单独作 preset**（`E-CAPABILITY-004`），只能作修饰 |
| ⬜ **D 属性级控制（AttributeSpec）** | 逐属性（音高/气声/亮度…）控制 | 依赖 `attribute_control` 能力位；三候选当前**均未验证**，Phase 2 才知道能否做 |

现行 `style.emotion` 枚举（契约已冻结，**改它属于 BREAKING**）：`neutral` `happy` `sad` `angry` `fear` `surprise` `tender` `professional` `tired` `excited`。
场景枚举（7 类）：`播报` `客服` `陪伴` `讲故事` `车载` `ASMR` `教学`。

**建议理由**：B 是「参数化细调」承诺的最小可证明形态；C/D 依赖尚未实测的能力位，先不做承诺（D19 实测后再升）。

**不拍板的后果**：StyleSpec 的控制手段优先级与 Q5/Q6 门禁无法定稿；preset 设计无边界。

## 10. D10 · 交付形态

**问题**：最终以什么形式交给使用者？

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| 🟢 **A 本地权重 + 私有 API（Docker）** | 交付权重 + 镜像，使用方在自己环境部署 | 与「禁商用」许可一致；升级与支持需版本管理；**不能对公众托管**（NC 边界） |
| ⬜ **B 公有云托管服务** | 我们托管，用户按 API 调 | 若面向公众即属「Hosted Service」，与 PolyForm NC 的自用/非商业边界冲突，须先走商业授权；成本与合规陡增 |
| ⬜ **C 离线 SDK / 嵌入式** | 打包进客户端设备 | 端侧算力与量化质量（R-10）风险；权重外泄风险高 |

**建议理由**：A 与 ADR-0001 的许可结构完全自洽（NC 覆盖自有增量、双层授权留商业口），且水印默认 true（`render.watermark`）能落地。

**不拍板的后果**：部署拓扑、监控告警、降级链、发布前检查单（[DEPLOYMENT-SPEC](../implement/serve/DEPLOYMENT-SPEC.md)）都只能停在「按建议假设」状态。

## 11. D11 · 许可条款法务定稿（非选项，是前置）

**问题**：PolyForm NC 1.0.0 + 双授权 + NOTICE 归因这套结构，需要法务签字才能发布权重。
**它不是「选哪个」，而是「由谁签、什么时候签」**：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| 🟢 **A 内部法务评审** | 内部法务/合规出书面意见，逐条确认 L-1–L-6 | 快；但内部意见对外部纠纷不具同等效力 |
| ⬜ **B 外部律所** | 委托律所出具意见书 | 慢、有成本；对外可信度高 |
| ⬜ **C 暂不发布权重** | 只发代码与规格，权重不出门 | 可立即推进；但项目「声音训练」的核心价值被扣住 |

**不拍板的后果**：**G0-2 未过 → 权重不得发布**（代码与文档可以继续推进）。
细化清单见 [LICENSING-IMPLEMENTATION-SPEC](../implement/legal/LICENSING-IMPLEMENTATION-SPEC.md) §2（L-1–L-6）与 §3（R-14b 九项）。

## 15. 三处冲突与消解方案（**待你确认**）

拍板结论里有 3 处与已冻结的规格/原则冲突。我**不擅自改写你的选择**，也不假装没有冲突——下面各给一个「保留你的选择、但补硬约束」的消解方案，确认后我写进 v0.5。

### 15.1 D5=C（云端 TTS 作生产兜底）↔ D21「本地权重 + 私有 API」+「不静默降级」

**冲突点**：v0.4 的 D21 是「本地权重 + 私有 API，不入公有云托管」；`E-CAPABILITY-001` 明文「**不静默降级**」。生产兜底恰恰是「不达标时悄悄换成云端」。

**消解方案（保留 D5=C）**：兜底作为**部署方可选启用的外挂**，而不是交付物内置默认。补 4 条硬约束：

| # | 约束 | 落点 |
| --- | --- | --- |
| 1 | **显式标记**：兜底时响应头 `X-Audit-degraded: true` + `audit.degraded=true`（字段已存在，不改契约） | [DEPLOYMENT-SPEC](../implement/serve/DEPLOYMENT-SPEC.md) 降级链 |
| 2 | **可关闭且默认关**：用**部署配置** `fallback.enabled: false` 控制，**不新增 VoiceSpec 字段**（避免契约 BREAKING） | DEPLOYMENT-SPEC 配置项 |
| 3 | **第三方 ToS 核验**：兜底所用云服务是否允许「作为他方产品后端」，多数商用 API 的 ToS 禁止或需企业协议 → 新增风险项 **R-25**，并入 G0-3 | 主方案 §13 + [UPSTREAM-LICENSE-MATRIX](../licensing/UPSTREAM-LICENSE-MATRIX.md) |
| 4 | **双标注与告知**：兜底音频须带我方水印 + 注明为第三方合成；不得混入训练数据与 golden_set | DEPLOYMENT-SPEC + 数据流水线 |

> 如果你要的是「内置默认开启、对用户透明」，那就与「不静默降级」直接对抗，我不建议——这种情况请改回 D5=A。

### 15.2 D6=A（1× 5090 D V2 24GB 自有）↔ D2=C（两场景并重）+ D8=C（多语）

**冲突点**：v0.1 §硬件表写明 **H-1「无法做全量 SFT / 大 batch」，Phase 4 与偏好对齐需顺延或租用**。而档 B 的 16–20 周包含 SFT + DPO + 多音色/多语评测。

**真实后果（必须先说清）**：

| 项 | 24GB 单卡的结论 |
| --- | --- |
| P0–P3（核验 / 数据 / 基线 / 参数化控制） | ✅ 可行 |
| LoRA 级微调 + 推理 + 评测 | ✅ 可行（小 batch + 梯度累积 + 量化） |
| 全量 SFT | ❌ 不可行（显存不足） |

### 15.3 D11=C（暂不发布权重）↔ D10=A（交付本地权重）

**冲突点**：字面矛盾——A 要把权重交给使用方，C 说权重不出门。**两种可能的真实意图，指向完全不同的 v0.5**：
